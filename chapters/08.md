## Спільні риси багатьох речей

Природа любить повторювати форми. Крило птаха і крило метелика влаштовані по-різному, але обидва вміють те, що ми називаємо «летіти». Програмування стикається з тим самим: є багато різних типів, які вміють одне й те саме. Rust дає для цього два близькі поняття — *узагальнення* (generics) і *трейти* (traits). Сьогодні вони звучать книжно, але за годину стануть простими, як дихання.

## Чому одного типу мало

Уяви функцію, що знаходить найбільше з двох значень. Можна написати окремо для чисел, окремо для слів:

```rust
fn bigger_u32(a: u32, b: u32) -> u32 { if a >= b { a } else { b } }
fn bigger_str<'a>(a: &'a str, b: &'a str) -> &'a str { if a >= b { a } else { b } }
```

Працює, але живої душі не спитаєш: якби типів було сім — довелося б сім разів повторювати те саме. І ось тут узагальнення дають свободу: замість конкретного типу ставмо букву — параметр типу:

```rust
fn bigger<T>(a: T, b: T) -> T
where
    T: Ord,
{
    if a >= b { a } else { b }
}
```

Тут `T` — це «будь-який тип», який задовольняє вимогу: він має вміти порівнюватися (`Ord`). Назва `T` — це просто звичка, можна й `Sky`; головне — послідовність. Тепер одна функція обслуговує і числа, і рядки, і все, що вміє порівнювати.

## Що таке трейт

Трейт — це опис здатностей. Він каже: «будь-хто, хто заявляє, що є носієм цього трейта, мусить мати ось ці методи». Уявімо, що ми хочемо вміти «представлятися» — мати ім'я:

```rust
trait Named {
    fn name(&self) -> String;
}
```

Далі трейт утілюють окремі типи. Для структури зірки і для структури місяця реалізація може бути різною, але зовнішній запит — однаковий:

```rust
struct Star { name: String }
impl Named for Star {
    fn name(&self) -> String { self.name.clone() }
}

struct Moon;
impl Named for Moon {
    fn name(&self) -> String { "Місяць".to_string() }
}
```

Це ключ до всього: `impl Trait for Type` — реалізація трейта для типу. Один і той самий запит «хто ти?» дає різні відповіді для різних типів. Поліморфізм у його ввічливій, рідній формі.

## Упорядковувати спільне

Тепер поєднуємо: функція, що приймає будь-кого, хто вміє називатися:

```rust
fn announce<T: Named>(item: T) {
    println!("Ласкаво прошу: {}", item.name());
}
```

Після двокрапки в куточних дужках стоїть вимога: `T` має реалізовувати `Named`. Компілятор не дасть передати туди тип, який не вміє називатися — і ти не отримаєш загадкової помилки пізно вночі, лише ясне «обмеження не виконано» ще під час збірки.

Є ще коротша форма — `impl` безпосередньо в параметрі:

```rust
fn greet(item: impl Named) {
    println!("Вітаю, {}!", item.name());
}
```

Вона читається природно: «дай мені будь-що, що вміє назватися». Різниця — лише синтаксична: `impl Trait` зручний для простих випадків, а явна `T: Trait` — коли потрібно, щоб один тип фігурував у кількох параметрах або поверненні.

## Вбудовані здатності

Rust приносить із собою багато готових трейтів — здатностей, які вже описані й спільно використовуються всіма крейтами. Це ніби домовленість про спільну мову:

- `Debug` — уміє друкувати себе у формі, зручній для налагодження;
- `Clone` — уміє створювати точну копію себе;
- `Copy` — вміє копіюватися непомітно (як числа);
- `PartialOrd`, `Ord` — уміють порівнювати;
- `Iterator` — уміють перелічувати свої елементи.

Якщо ти хочеш, щоб твоя власна структура вміла «представитися» налагоджувачу — додай це простим рядком:

```rust
#[derive(Debug, Clone)]
struct Firefly {
    flashes: u32,
}
```

`#[derive(...)]` — це спосіб сказати: «зроби стандартно, не пиши рук руками». Компілятор сам напише реалізації `Debug` та `Clone`. Ти лише відмічаєш галочки в списку здатностей, як записуєш учня в гурток.

## Цінність одного словника

Один із найважливіших трейтів — `From`. Він описує перетворення: «з мене можна отримати інше». Приклад: з рядка можна отримати `String`, з `&str` — `String`, з числа — рядок. Ці домовленості дозволяють писати код, який приймає найприродніший тип і перетворює його тоді, коли треба:

```rust
fn to_string_soft<T: ToString>(value: T) -> String {
    value.to_string()
}
```

Такі загальні межі створюють словник, зрозумілий усій екосистемі. Ти не мусиш учити чужий діалект кожного крейта: домовленості `From`, `Debug`, `Clone`, `Iterator` — це спільна мова, на якій Rust-спільнота розмовляє роками.

## Чуттєва сутність трейтів

Якщо узагальнити образно, трейти — це як риси характеру. «Товариський», «спокійний», «уважний до деталей» — це не самі типи, це описи того, як людина поводиться. І якщо зірка — «Добра ім'я мати», це не робить її копією місяця; просто обидва можуть бути «іменованими». Світ мови стає багатшим, коли ми описуємо поведінку, а не лише форми.

Державність не залежить від розміру: маленький мураха і велике дерево однаково «живі». Так і трейти дозволяють нашим типам різного розміру й походження брати участь в одних і тих самих, спокійних розмовах.

## Як крейти втілюють трейти для своїх типів

Кожен крейт може зробити свої типи «учасниками» спільних трейтів, і це велика сила: тоді твої типи говорять тією ж мовою, що й усе в екосистемі. Уяви крейт для календаря: він визначає тип `MoonPhase` (фаза місяця). Якщо він реалізує для нього `Debug`, `Clone`, `Copy` — твій код може друкувати фазу, копіювати її, а якщо ще й `PartialEq` — порівнювати фази між собою.

```rust
#[derive(Debug, Clone, Copy, PartialEq)]
enum MoonPhase {
    New,
    Crescent,
    Quarter,
    Gibbous,
    Full,
}
```

Тепер у будь-якому місці, де ти очікуєш здатності «бути надрукованим» або «бути рівним», фаза місяця — повноправний учасник. Це конвенція спільноти: крейти одягають свої типи у стандартні трейти, щоб чужий код не мусив домагатися особливого поводження.

## Методи з обмеженнями

Трейти дозволяють писати методи, які існують *лише для певних* типів. Розгляньмо `Vec<T>`: він має метод `sort`, але тільки тоді, коли `T` вміє порівнюватися (`Ord`):

```rust
let mut numbers = vec![3, 1, 2];
numbers.sort();   // можна: i32 уміє порівнюватися

// якби T не вміло — методу просто не було б у цьому типі
```

Це називається «умовна реалізація». Ти бачиш метод у документації, лише коли умова виконана. Мова наче сортує інструменти в ящику: не всі вони лежать на поверхні, а лише ті, які потрібні саме твоєму типу. Звучає складно, а «на пальцях» це просто домовленість: не обіцяй того, чого не вмієш.

## Приклад власного трейта: звук

Давай створимо собі маленький трейт і зробимо кілька типів його носіями. Нехай усі, хто вміє «звучати», мають метод `sound`:

```rust
trait Sound {
    fn sound(&self) -> String;
}

struct Wind { is_quiet: bool }
struct Night {
    crickets: u32,
}

impl Sound for Wind {
    fn sound(&self) -> String {
        if self.is_quiet {
            "дмух...".to_string()
        } else {
            "дмух-дмух-дмух!".to_string()
        }
    }
}

impl Sound for Night {
    fn sound(&self) -> String {
        if self.crickets == 0 {
            "повна нічна тиша".to_string()
        } else {
            format!("цвіркун у {crickets} передзвонах", crickets = self.crickets)
        }
    }
}
```

Тепер функція може приймати «будь-що, що вміє звучати»:

```rust
fn listen<T: Sound>(thing: T) {
    println!("чуємо: {}", thing.sound());
}
```

Зверни увагу, як це об'єднує: ми не знаємо, що саме приходить (вітер чи ніч), але знаємо, що можемо викликати `sound`. Ми описуємо поведінку, не знаючи конкретики. Це дозволяє пізно знаходити те, що справді важливо.

## Трейти як контракти для майбутнього

Є ще глибший сенс: трейти — це контракти між письменником і читачем коду. Коли ти бачиш у сигнатурі «`T: Read`», ти одразу знаєш: це може прочитати щось (файл, мережа, буфер), і тобі доступні методи читання. Ніхто не має знаходити цей факт під шаром голих функцій — контракт видно з першої літери.

Так утворюється мова екосистеми. `From`, `Into`, `Iterator`, `Debug`, `Display` — це звичайні «слова», які ти вчиш один раз, а потім зустрічаєш у більшості крейтів. Заощаджена увага — величезний ресурс: вона йде на *ваше*, а не на переклад чужих діалектів.

## Уявімо метод, якого немає

Щоб відчути цінність трейтів, спробуй уявити Rust без них. Кожен крейт мав би свій приватний спосіб «надрукувати себе», «порівняти» і «скопіювати». Коду ставало б більше, думка — заплутана, а спільні операції — неможливі без шарів налаштувань.

Трейти — це той «спільний протокол», завдяки якому десятки тисяч крейтів живуть в одному домі мирно. Опанувавши їх, ти зрозумієш мову не як набір команд, а як спільноту з формами взаємодії. Прийде спокій: усе вже домовлено, залишилось лише підключитися.

## Вправа на вечір

Нехай твій тип `Firefly` вміє «світитися» — створи маленький трейт `Glow` з методом `glow(&self) -> u8`, де результат означає силу світла (0 — темно, 255 — яскраво). Реалізуй його для двох-трьох різних типів: світляка, ліхтарика і зорі. Потім напиши функцію, яка приймає `impl Glow` і друкує рівень світла.

Це вправа не на інструменти, а на усвідомлення: поведінка відокремлюється від типу. Світляк, ліхтарик і зоря — різні, але всі «вміють світити». Так само в реальному коді: різні типи об'єднуються в одну поведінкову родину.

## Статична диспетчеризація: мономорфізація

Коли ти пишеш `fn process(item: impl Speak)`, компілятор знає *на етапі збірки*, який саме тип стоїть за `item`. Він генерує окрему копію функції для кожного типу — це називається *мономорфізація*. Результат: жодних зворотних викликів, жодних втрат. Код летить.

Зворотний бік — більший бінарний файл (кожен тип — свій варіант функції), але ціна мінімальна, і швидкість максимальна. Саме тому `impl Trait` — улюблений спосіб для швидкого, предикативного коду.

## Динамічна диспетчеризація: trait-об'єкти

Є й інший шлях — `Box<dyn Speak>`. Тут компілятор *не знає* наперед, який тип прихований за вказівником. Він зберігає «таблицю віртуальних методів», і під час виклику шукає правильну функцію в runtime. Це *динамічна* диспетчеризація.

```rust
fn announce(speakers: Vec<Box<dyn Speak>>) {
    for s in speakers {
        s.speak();
    }
}
```

Це менш швидко, але більш гнучко: ти можеш зібрати колекцію *різних* типів, які всі мають `Speak`. Вибір між статичною і динамічною диспетчеризацією — не про «добре чи погано», а про «швидко чи гнучко».

## Контракти трейтів: коли код — угода

Трейт може мати *умови* (constraints): «для того, щоб реалізувати цей трейт, тип повинен мати ось це». Наприклад, `Display` потребує, щоб тип був `fmt::Debug`:

```rust
use std::fmt;

trait PrettyPrint: fmt::Display {
    fn pretty(&self) -> String {
        format!("[{}]", self)
    }
}
```

Це «контракт»: якщо тип хоче бути `PrettyPrint`, він уже мусить бути `Display`. Компілятор перевіряє контракт на етапі збірки. Жодних сюрпризів у runtime.

## Трейти-обмеження у функціях

Коли функція приймає загальний тип, вона часто каже «але тільки такий, який має ось ці можливості»:

```rust
fn largest<T: PartialOrd>(list: &[T]) -> &T {
    let mut largest = &list[0];
    for item in &list[1..] {
        if item > largest {
            largest = item;
        }
    }
    largest
}
```

`T: PartialOrd` — це «будь-який тип, який вміє порівнювати». Якщо ти передаси тип, який не реалізує `PartialOrd` — компілятор скаже «ні». Це не обмеження заради обмеження; це спосіб сказати «я потребую цієї якості, і вона перевіряється».

## Деструктуризація через трейти

Трейт `Into` дозволяє перетворювати один тип на інший:

```rust
let name = String::from("Руст");
let greeting: String = format!("Привіт, {name}!");
```

Це не деструктуризація в строгому сенсі, але природний рух даних: одне значення перетворюється на інше, без втрати. `Into` — один із найпоширеніших трейтів, і ти зустрічатимеш його щодня.

## Вправа на вечір

Спробуй написати трейт `Describable` з методом `describe()`, який повертає `String`. Реалізуй його для `String`, `i32` та `Vec<i32>`. Потім напиши функцію, яка приймає `&dyn Describable` і друкує результат. Це проста вправа, але вона дасть відчуття: трейти — це не «теорія», а спосіб, яким ти розмовляєш зі своїми типами.

## Автореалізація та порожні трейти

Деякі трейти позначають «властивість» без власних методів. `Copy` — такий: він майже порожній, але каже компілятору «цей тип можна копіювати бездумно». Так само `Send` і `Sync` — «це можна передати чи позичити потокам». Їх часто називають «маркерами».

```rust
struct Ticket {
    number: u32,
}

// кажемо: Ticket можна копіювати
impl Copy for Ticket {}
impl Clone for Ticket {
    fn clone(&self) -> Self {
        *self
    }
}
```

Маркери-трейти — це «етикетки» на типах: вони не додають поведінки, але змінюють правила дозволу. Компілятор сам «пам'ятає», що значить кожен маркер. Часто ти навіть не реалізовуєш їх вручну, а використовуєш `#[derive(Clone, Copy)]`.

## Селекторна реалізація: `Self`

У реалізації трейта через `Self` мається на увазі «цей самий тип», який реалізовує трейт. Це дозволяє писати функції загального вигляду, щоб не повторювати імена.

```rust
impl Clone for Point {
    fn clone(&self) -> Self {
        Point { x: self.x, y: self.y }
    }
}
```

Тут `Self` — це `Point`. Такий запис коротший і зрозуміліший: читач не мусить дивитися на початок блоку, щоб зрозуміти тип. `Self` — частий гість у реалізаціях, і він робить код чистішим.

## Трейти та загальні типи глибше

Коли декілька обмежень зустрічаються разом, Rust дозволяє з'єднувати їх знаком `+`:

```rust
fn display<T: std::fmt::Debug + Into<String>>(v: T) {}
```

Це «і те, і те». Такі комбінації дають гнучкість: функція потребує кількох якостей водночас. Синтаксис може стати гучним, але сенс прозорий — «мені потрібен тип, який уміє робити ось це і ось це».

## Об'єкти-трейти розміром з `Box`

Ми бачили `&dyn Speak` — динамічну диспетчеризацію. Її можна перенести в `Box<dyn Speak>`, щоб володіти об'єктом, не знаючи його точного типу:

```rust
fn new_speakers() -> Vec<Box<dyn Speak>> {
    vec![
        Box::new(Robot { id: 1 }),
        Box::new(Dog { name: "Рекс".to_string() }),
    ]
}
```

Тут `Vec` тримає різні типи під однією «парасолькою» трейта. Це потужність: ти збираєш у колекцію різні сутності, які всі вміють `Speak`, і обробляєш їх однаково. Динамічна диспетчеризація розплачується невеликою швидкістю, але дає цю гнучкість.

## `impl Trait` як позиція та повернення

Ми бачили `impl Trait` в аргументах. Його можна використати і у поверненні: функція обіцяє «щось, що реалізовує цей трейт», не називаючи точно.

```rust
fn double_numbers() -> impl Iterator<Item = u32> {
    (1..=3).map(|n| n * 2)
}
```

Такий запис зручний, бо повертає ланцюжок ітератора, тип якого складно назвати руками. Компілятор знає точний тип, а ти — ні. Це не «трюк», а елегантність: оголошуючи інтерфейс, ти ховаєш деталі. У `impl Trait`-поверненні «закрите» тип об'єкта твоєю обіцянкою.

## Методи трейта за замовчуванням

Трейт може мати методи, що мають *стандартну реалізацію* всередині `{}`, яку реалізатор може перевизначити або лишити. Це зменшує рутину: тобі не треба повторювати однакову логіку в кожному типі.

```rust
trait Perimeter {
    fn side_lengths(&self) -> u32;

    fn perimeter(&self) -> u32 {
        self.side_lengths() * 4 // стандартний випадок — квадрат
    }
}
```

Кожен тип мусить дати `side_lengths`, але `perimeter` уже готовий. Якщо комусь потрібен інший — він перевизначить. Так трейт стає «привітливим»: мінімум обов'язку, максимум гнучкості.

## Звуження до трейта чи розширення обмежень

Коли пишеш загальну функцію, виникає маленька дилема: наскільки «вузько» обмежити тип? Вузько — швидше й чесніше; широко — гнучкіше, але менш ясно. Правило, яке допомагає: *найменше обмеження, яке ще передає сенс*.

```rust
fn print_sizes<T: std::fmt::Debug>(x: &T) {}
```

Якщо функція лише друкує, чи справді їй треба, щоб тип «вмів» десять речей? Часто достатньо `std::fmt::Debug`. Менше обмежень — легше використати функцію, але розмитіша мета. Збалансуй, і код стане і другом, і точним.

## Вправа на вечір: зв'язати трейт і перелік

Щоб об'єднати дві попередні ідеї, зроби таку вправу: опиши перелік `Shape` (коло, квадрат, трикутник) з полями розмірів. Нехай трейт `Area` має метод `area(&self) -> f64`, і реалізуй його для кожного варіанта. Тоді напиши функцію, яка приймає `&dyn Area` і друкує площу.

Це кілька рядків, але вони показують, як переліки й трейти працюють пліч-о-пліч: перелік — форма даних, трейт — поведінка. Кожен варіант — свій «житель» із власною формулою, а спільна назва `Area` збирає їх разом.

## Медитація на ніч

Сьогодні ми відкрили дві теми, які звучать страшно, а означають добре: узагальнення — це одна функція на багато типів, трейти — це домовленості про здатності. Разом вони дають гнучкість без плутанини: компілятор слідкує, щоб усе, що ти передаєш, насправді вміло те, що ти просиш.

Не запам'ятовуй усі назви. Відчуй: форма першого порядку, а над формою — здатність. «Що це робить», а не лише «що це таке».

> Крило і крило — різні,
> але обидва вміють летіти.
> Форма описує, чим річ є;
> здатність — що вона вміє.
> Спокій — коли про рух домовлено
> ще до польоту.

До наступної глави. Добраніч.
