## Надійність, перевірена тишею

Усе, що ми вивчили досі, — власність, типи, помилки, конкурентність — захищає нас від цілого класу нещасть ще під час збірки. Але є ще один шар надійності, який залежить від людини: відповідність коду твоєму задуму. Як знати, що програма справді робить те, що ми думаємо? На це є відповідь: тести.

Тести — це не нав'язане зайве. Це твоя розмова з самим собою під час тихої години: «я думаю, ця функція робить ось це — давай перевіримо, чи так воно є».

## Перший тест

Почнемо з маленької функції, яка вміє рахувати слова:

```rust
pub fn count_words(text: &str) -> usize {
    text.split_whitespace().count()
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn count_simple() {
        assert_eq!(count_words("тиша і спокій"), 3);
    }
}
```

Зверни увагу на скелет. `#[cfg(test)]` — це напис «цей модуль живе лише під час тестів». `#[test]` — позначка «це — тест, Cargo має його прогнати». `use super::*` приносить надбання батьківського модуля. А `assert_eq!` — це перевірка рівності: якщо ліва і права частини розходяться, тест провалиться з поясненням.

Запускаємо:

```text
cargo test
```

Cargo проганяє всі тести й доповідає. У цьому ритуалі є магія: ти робиш заявку, машина її перевіряє, і за хвилину ти знаєш, чи ти вірно розумів свій код.

## Сутність перевірки

Найтонший момент тестування — обрати, що перевіряти. Добре працювати з трьома настановами: перевіряй звичайний шлях, перевіряй крайові випадки, перевіряй, що нещастя оброблені достойно.

```rust
#[test]
fn empty_text_has_zero_words() {
    assert_eq!(count_words(""), 0);
}

#[test]
fn whitespace_only_counts_nothing() {
    assert_eq!(count_words("   "), 0);
}
```

Перший тест перевіряє порожній рядок, другий — рядок з одним лише пробілами. Саме в таких, здавалося б, дрібних місцях ховається більша частина несподіванок. Край гадає: де межа? Тест підказує, що там усе гаразд.

## Чудові помічники: assert і не тільки

Друзі перевіряючого зачіпають ширше, ніж `assert_eq`. Є `assert` — для справ, `assert_ne` — «не рівні», `assert!` — для умови:

```rust
#[test]
fn positive_number_passes() {
    let n: i32 = 5;
    assert!(n > 0, "число {n} мало бути додатним");
}
```

Зауваж повідомлення після коми у `assert!`: воно з'являється, якщо тест падає, і рятує твій спокій уночі — ти одразу бачиш, у чому розбіжність, а не гадаєш над загальним текстом.

## Тести, які чекають на невдачу

Інколи ми хочемо перевірити не те, що код працює, а те, що він *правильно падає*. Rust має для цього позначку `#[should_panic]`:

```rust
#[test]
#[should_panic]
fn out_of_bounds_panics() {
    let items = [1, 2, 3];
    let _ = items[99];
}
```

Тест проходить лише тоді, коли код справді панікує. Це не заохочення паніки, а свідчення гігієни: якщо ми очікуємо, що край зупиниться криком — нехай він кричить тим самим способом, який ми домовлялися.

## Тримати тести ближче до коду

У Rust тести зазвичай живуть поруч із кодом, який вони перевіряють, — у тому самому файлі, у модулі `tests`. Це глибше, ніж просто зручність: ти завжди бачиш роботу і її перевірку, коли відкриваєш файл. Немає відстані між питанням і відповіддю.

Є й окремий світ для інтеграційних тестів — `tests/` у корені проєкту: там ти перевіряєш, як твій крейт читається *ззовні*, як ним користується чужа програма. Це як запросити гостя і подивитися, чи зручно йому в домі.

## Надійність як звичка

Тести дають спокій не лише тепер, а й потім. Розвиваєш код — змінюєш щось велике — і раптом один із тестів почервонів. Не «десь щось зламалося», а «ось саме ця функція більше не вміє того, що обіцяла». Тест ловить регресію — повернення назад — не по спогадах, а по фактах.

Програми з тестами — це сади зі стежками, по яких уже ходили: кожен новий відвідувач може пройти тими самими стежками і знати, що вони не ведуть у прірву. Без тестів сад може виглядати так само — але ти не знаєш, чи не звучить десь тихо тріщина.

## Що робить `cargo test` докладно

`cargo test` — це не лише «прогнати тести». Це ціла церемонія з багатьох етапів: спершу збірка (з усіма перевірками типу), тоді виконання кожного тесту в окремому процесі (щоб збій одного не псував інших), а в кінці — звіт.

Розгляньмо частину звіту, яку ми бачили раніше:

```text
running 8 tests
test render_markdown_headings_and_paragraphs ... ok
test render_markdown_code_fence_is_escaped ... ok
...
test result: ok. 8 passed
```

Кожен тест — окремий рядок, і ти бачиш: ім'я, стан, час. Коли все зеленим — тепло. Коли один червоний — він показує, де саме: ця точність і є сила тестів. Тобі не треба гадати «а де випало» — тести вказують пальцем.

## Тести як співрозмовники майбутнього

З часом тести перетворюються на *документацію*, яка розповідає, як твій код має поводитися. Новий розробник, який прийшов у проєкт, може прочитати тести і зрозуміти наміри: «ця функція має повертати порожній рядок для порожнього входу, ось доказ».

Це начебто мало, але насправді безцінно: код каже «що», а тести кажуть «чому так». Разом — повна розмова. Тому варто писати тести не лише для «першої версії», а й додавати їх, коли виправляєш баги: кожен баг, який ти знайшов, має залишати по собі тест, що його ловить назавжди.

## Три рівні тестів

Спільнота розрізняє три рівні перевірок, і вони виглядають так:

1. **Юніт-тести** — найменші: перевіряють одну функцію або один метод. Живуть поруч із кодом у модулях `tests`.
2. **Інтеграційні тести** — перевіряють, як твій крейт працює «ззовні»: чи імпортуються умови, чи повертаються правильні результати, чи кожна публічна функція коректна. Живуть у каталозі `tests/` у корені проєкту.
3. **Доктести** — приклади в документації, які збираються як тести.

Три рівні — не бюрократія, а повний захист: найдрібніші справи перевіряються прямо біля себе, ширші — на межі крейта, а обіцянки «прикладу» — мовою документації.

## Харизма `should_panic`

Деякі тести мають «позитивну негативність»: вони перевіряють, що код справді падає тоді, коли має. Погляньмо ще раз, як це виглядає на корисному прикладі — парсер, який має падати на невірному вході:

```rust
#[test]
#[should_panic(expected = "невірний формат")]
fn bad_format_panics() {
    parse_things("не число");
}
```

Позначка `expected` вказує, яке саме повідомлення паніки ми чекаємо. Це навіть точніше, ніж просто «має впасти»: воно каже «має впасти саме тут і саме так». Нехай падіння стане причиною не страху, а передбаченості.

## Тести з погляду часу

Є одна якість гарних тестів, про яку рідко говорять уголос: *вони швидкі*. Якщо тест виконується секунди, ти запускаєш його десятки разів на день, без вагань. Якщо хвилини — ти починаєш уникати запуску, і вони втрачають сенс. Тому:

- тримай тести малими й цілеспрямованими;
- не покладайся в тестах на реальну мережу чи годинник — вони непередбачувані;
- якщо важка перевірка вкрай потрібна — дай їй помітку `#[ignore]`, і нехай вона чекає особливого запуску.

Це догляд за інструментом. Тест, який ти біжиш легко, — інструмент, який рятує кожного дня.

## Тестування перед сном

Перед завершенням зупинись на секунду: тести — це не «додаткова робота». Це спосіб записати між сторінками коду, як він *має* жити. Коли ти декілька разів побачиш, як тест рятує тижневу роботу від регресії — ти вже не спитаєш «навіщо тести», ти спитаєш «як я жив без них».

І приємна особливість Rust: вся інфраструктура тестів вбудована і проста. Не потрібно жодних зовнішніх фреймворків для початку — `#[test]` і `cargo test` — це вже весь стіл, за яким можна влаштуватися щовечора.

## Документаційні тести: магія, яка вчить

Ми згадували доктести в минулій главі; тут дозволимо собі глибший вдих. Доктести — це не просто «код у коментарях». Це тест, який одночасно пояснює та перевіряє. Якщо приклад у документації працює — значить, він не обманює.

```rust
/// Додає два числа.
///
/// ```
/// let result = rust_book::add(2, 2);
/// assert_eq!(result, 4);
/// ```
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}
```

Коли ти пишеш `cargo test`, компілятор бачить приклади з `rust` та іншими мовами-оголошеннями, і запускає їх. Вони живуть у тому самому інтеграційному середовищі, що й решта тестів: тобто можуть використовувати твій крейт, імпортувати функції, робити помилки, які компілятор покаже.

Це чудовий спосіб «вбити кількох зайців»: ти пишеш документацію, яка ще й перевіряється. Якщо зміниш логіку, а приклад не оновиш — тест покаже розбіжність, і ти відразу побачиш, що «завтрашній читач» отримає хибну відповідь.

## Інтеграційні тести: кордони крейта

Коли бібліотека стає більшою за один файл, з'являються інтеграційні тести. Вони живуть у каталозі `tests/` на рівні кореня проєкту і імпортують твій крейт як зовнішній. Це важливо: вони не бачать приватних деталей, вони бачать лише те, що ти вирішив показати.

```rust
// tests/integration_test.rs

use rust_book::first_word;

#[test]
fn first_word_works() {
    assert_eq!(first_word("hello world"), "hello");
}
```

Каталог `tests/` — це «зовнішній світ» твого крейта. Кожен файл там — окрема збірка, окремий тест-прогін. Завдяки цьому ти знаєш, що крейт працює не тільки «всередині», а й «зовні», так, як його використовують клієнти.

## Мета-тестування: тести для тестів

Існує також поняття «тест для тесту». Це не жарт: інколи ти хочеш упевнитися, що тест *спрацює* навіть у неправильному середовищі, або перевірити, що тест-код не містить помилок компіляції (хоча це рідкість). Але частіше під «тест для тесту» мають на увазі спосіб перевірити, що певні функції коректно обробляють крайові випадки. Для цього можна написати кілька окремих тестів з різними назвами та різними входами.

У Rust це природно: кожен `#[test]` — окрема «лялька», яку можна налаштувати по-своєму. Багато маленьких функцій-тестів краще за одну велику, бо вона часто об'єднує кілька питань у купу.

## Тестування асинхронного коду

Ми зустрічали асинхронність у шостій главі. Її тести — окрема історія: `#[tokio::test]` — це швидкий спосіб запустити тест в асинхронному середовищі:

```rust
#[tokio::test]
async fn async_example() {
    let result = tokio::time::sleep(std::time::Duration::from_millis(10)).await;
    assert!(true);
}
```

Це «той самий тест», але з двигуном: асинхронні виклики працюють, бо є runtime. І тут працює все те саме: `assert`, `should_panic`, `ignore` — усі звичні правила, тільки з додатковим `.await` усередині.

## Пріоритети: що тестувати спочатку

Неможливо перевірити все одразу. Ось система пріоритетів, яка працює:

1. **Крайові випадки.** Порожні входи, максимальні значення, нульові значення — там, де код може «зламатися» через неочікувану ситуацію.
2. **Загальний шлях.** Ті функції, які викликаються найчастіше.
3. **Логічні межі.** Функції, які приймають складні аргументи (як от структури, переліки, `Result`).

Не витрачай часу на «красиві» тести, поки не закриті перші два пункти. А коли обидва закриті — розширюй на спокій.

## Тести, які «живуть усередині»

Деякі функції настільки критичні, що їхні тести живуть поруч із кодом, а не в окремому файлі. Це нормально й рекомендується: чим ближче тести до функції, тим легше їх читати й підтримувати.

Така «модульна» структура — класичний підхід Rust: `lib.rs` або `main.rs` містять модуль `tests`, який містить усі маленькі функції-перевірки. Такий порядок не обов'язковий, але дуже зручний, особливо на початку проєкту, коли ти не хочеш розкидати код по файлах.

## Метрики: скільки часу йде на тестування

`cargo test` показує час виконання кожного тесту. Це не забавка, а цінна інформація: якщо один тест займає секунди, можливо, він занадто «важкий» для свого рівня. Можливо, його варто розділити або перенести в інтеграційний рівень.

Контроль часу — це така сама форма турботи, як контроль помилок: ти не хочеш, щоб тестування ставало в тягар, ти хочеш, щоб воно було безкоштовним.

## `-- --nocapture`: побачити те, що друкує тест

У дефолтному режимі `cargo test` приховує текст, який тест друкує з `println!`. Це корисно, бо екран не забивається. Але коли хочеш побачити вивід — передай прапорець `-- --nocapture`:

```text
cargo test -- --nocapture
```

Після `--` ідуть аргументи для самого тестового бінарника. `--nocapture` каже: «не ховай вивід». Це особливо зручно під час налагодження: ти бачиш, що саме друкує твій тест, не читаючи «невидимий» текст. Між двома `--` і самим тестом стоїть тонка, але важлива грань.

## Ієрархія тестів: розділення за цілями

Чим більший проєкт, тим більше сенсу розділяти тести за «цілями». Розділення не обов'язкове, але зручне: малі «юніт-тести» для функцій, «інтеграційні» для меж крейта, «доктести» для документації. Кожен рівень відповідає на своє запитання.

- Юніт-тест питає: «ця функція повертає те, що обіцяла?»
- Інтеграційний тест питає: «мій крейт працює так, як його використовують ззовні?»
- Доктест питає: «приклад у документації не обманює?»

Розділення цілей не створює бюрократії; воно народжує ясність. Коли тест провалюється, ти одразу знаєш, на якому «поверсі» шукати причину.

## Скорочення повтору в тестах: бібліотеки-помічники

Часто тести мають повторюваний вступ: створити об'єкт, налаштувати стан, виконати крок. Щоб не дублювати, можна винести допоміжні функції в спільний модуль тестів. Це не «магія», а звичайна гігієна коду, перенесена в тести.

```rust
#[cfg(test)]
mod tests {
    fn sample_point() -> Point {
        Point { x: 1, y: 2 }
    }

    #[test]
    fn x_is_one() {
        assert_eq!(sample_point().x, 1);
    }
}
```

Тут `sample_point()` — помічник, що збирає об'єкт для тестів. Повторення зникає, тести лишаються короткими та читабельними. Це дрібниця, але вона звільняє голову для справжніх питань.

## Інкрементальні пороги: `assert` далі

Крім `assert_eq!` і `assert_ne!`, існують вибагливіші перевірки. Наприклад, `assert!(a < b)`, який перевіряє загальну умову, або `assert!(matches!(value, Some(_)))`, що перевіряє форму. Короткі — завжди має бути й повідомлення, якщо потрібно.

```rust
assert!(x < 100, "очікували, що {x} менше за сто");
```

Це «довільні» перевірки — вони ловлять не лише порівняння, а й будь-які умови, які ти хочеш закріпити. `matches!` дає ще один спосіб перевірити, чи значення пасує до патерну. Так ти розширюєш мову перевірок — і тести стають виразнішими.

## Підсумок: тести як довіра

Перед сном складемо те, що вже прочитано, в одну картину. Тести — це не «окрема робота», а спосіб *довіряти власному коду* без тривоги. Rust дає їм місце прямо в серці інструментарію: `#[test]`, `cargo test`, доктести, помічники — усе поруч, усе швидко.

Коли ти почнеш помічати, що тести «рятують» тижневу роботу за п'ять хвилин, — бажання питати «навіщо тести» зникне. Довіра приходить не з віри, а з перевірок — і тести знають це з самого початку.

## Тест — це договір із майбутнім

Сприймай тест не як схвалення собі, а як *договір із майбутнім тобою*. Ти кажеш: «я обіцяю, що ця поведінка триватиме». Через пів року, коли ти вже забув цей шматок, тест нагадає, що ти думав саме так.

Це змінює ставлення до написання тестів: ти пишеш їх не для компілятора, а для наступного читача — головно для себе. Тест = короткий запис наміру, який не дає зникнути. З кожним таким договором програма стає надійнішим домом для майбутніх змін.

## Один тест на одну поведінку

Часом тести пишуться великими та «перевіряють усе одразу». Це спокусливо, але ускладнює пошук причини, коли щось падає: не знаєш, яка саме обіцянка зламалася. Краща звичка — один тест на одну поведінку.

```rust
#[test]
fn empty_contains_nothing() { /* один присуд */ }

#[test]
fn inserted_is_found() { /* інший присуд */ }
```

Коли падає саме `inserted_is_found`, ти одразу знаєш, що порушено. Не треба розслідувати «що саме» у великому тесті. Малі тести — це чіткі повідомлення, а не загадка.

## Тримай тести швидкими

Чи ти помічав, що інколи не хочеться запускати `cargo test`, бо чекати? Тому тести мають бути *швидкими*. Повільний тест — це тест, який врешті ігнорують. Швидкість — частина звички.

```text
# швидкий loop-pattern: тримай одиничні тести легкими
cargo test
```

Якщо тобі треба протестувати важку, повільну операцію, — винеси важку частину за межі одиничного тесту або застосуй моки-замінники. Довгий тест — не «більш правильний», а менш привабливий для повтору. Бережи цю миттєвість.

## Переговірки перед сном: що робити, коли тест «посипався»

Рано чи пізно тест падає. Не лякайся — це запрошення до лупи. Прийом, який завжди рятує, називається «найменший приклад»: звузь задачу до найменшого коду, що відтворює провал.

1. Виділи порушену функцію.
2. Заміни великі входи на маленькі.
3. Виконай тест сам, стеж за кроками.

Зазвичай після такого «висповідання» причина стає видимою, ніби вона й чекала. Провал тесту — не поразка, а підказка, де тонка стежка. Подих, маленький приклад, і ти знову на ній.

## Медитація на ніч

Сьогодні ми дізналися, що тест — це перевірка між задумом і дійсністю, що Cargo проганяє їх одним словом, що в тебе є `assert` і `assert_eq`, що є спосіб перевірити навіть правильне падіння, і що тести живуть поруч із кодом, як стежки в саду.

Не перетворюй тести на повінь перевірок; пиши кожну відповідь саме там, де вона може навчити. Тест, який ніколи не падає, усе одно вчитель: він сказав тобі правду про твій задум.

> Тест — це питання до власного коду.
> Відповідь приходить тихою розмовою:
> "так, саме так я й думав",
> або: "стій — а тут не так".
> Стежки в саду — наші тести:
> перевірені, достовірні, відкриті.

До останньої глави. Добраніч.
