## Багато рук для багатьох справ

Приходить момент, коли однієї пари рук мало. Програма хоче робити кілька справ паралельно: слухати мережу і писати в файл, рахувати дві великі таблиці, відповідати багатьом користувачам одразу. Це називається конкурентністю — мистецтвом багатьох рук, які працюють в одному домі, не заважаючи одна одній.

У конкурентності найважче не розігнати кілька потоків, а навчити їх *ділитися*. Два будівельники однаково вдячні, доки обидва хочуть один молоток. Так і потоки: доки кожен робить своє — все чудово; коли обидва чіпляються за одні дані — починається плутанина.

## Свідчення Safe у самій мові

Rust підходить до конкурентності незвично: він не дає кілька додаткових конструкцій «просто так», а приносить нори рішень із двох трейтів, які вже зустрічалися нам. Їхні імена — `Send` і `Sync`, і вони описують здатності типів переїжджати між потоками.

- `Send` означає: «цей тип можна передати іншому потоку». Велика частина типів Rust — `Send`: числа, String, вектори.
- `Sync` означає: «на цей тип можна дивитися з кількох потоків одночасно через посилання».

Компілятор перевіряє ці здатності під час збірки. Ти не можеш ненароком передати між потоками щось, що розвалиться від цього. Це найбільший скарб Rust: конкурентна безпека перевіряється тим самим компілятором, який перевіряє власність, — тобто до запуску.

## Потоки — робітники

Розглянемо найпростішу форму багатозадачності — операційні потоки (`std::thread`):

```rust
use std::thread;
use std::time::Duration;

fn main() {
    let handle = thread::spawn(|| {
        println!("робітник почав");
        thread::sleep(Duration::from_millis(300));
        println!("робітник завершив");
    });

    println!("головний потік далі");
    handle.join().unwrap();
    println!("обе зійшлося");
}
```

`thread::spawn` створює новий потік; ми отримуємо ручку, через яку можна чекати завершення (`join`). Робітник працює тимчасом, поки головний потік іде далі. Коли головний вирішив почекати — образившись, ми беремо `join` і ввічливо дожидаємося.

## Спільний дім, спільні дані

Тепер про те, що викликає трепет у кожного програміста: обидва потоки хочуть скористатися спільними даними. Rust має для цього зброю — взаємне виключення, `Mutex`. Уяви замок з ключем: щоб торкнутися даних, треба взяти ключ; тримаючи дані для зміни — ти в замку, і лише ти; відпустив — і інший може увійти.

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let shared = Arc::new(Mutex::new(0i32));
    let mut handles = vec![];

    for _ in 0..4 {
        let shared = Arc::clone(&shared);
        handles.push(thread::spawn(move || {
            let mut guard = shared.lock().unwrap();
            *guard += 1;
        }));
    }

    for h in handles {
        h.join().unwrap();
    }

    println!("лічильник: {}", *shared.lock().unwrap());
}
```

Тут з'являються два знайомі нам ідеї в нових шатах. `Arc` — це посилене посилання: воно дозволяє кільком потокам тримати одне й те саме значення, і кожен тримач підраховується; коли останній піде — значення звільниться. А `Mutex` захищає сам доступ: лише один уміє писати за один раз.

Ми ще бачимо `move` перед замиканням — це каже: «візьми з собою цей `Arc`, він твій». Без `move` замикання спробувало б позичити ту саму ручку з кількох потоків — що є неможливим, бо позички не `Send`. Rust уже заздалегідь усе продумав: якщо ділишся — маєш поділитися чесно.

## Канали — листи між потоками

Можливо, простіший спосіб співпраці — не ділитися, а *листуватися*. Rust має канали (`channel`): один кінець надсилає повідомлення, інший — отримує. Це як дві кімнати з поштовою скринькою між ними.

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (sender, receiver) = mpsc::channel();

    thread::spawn(move || {
        for i in 1..=3 {
            sender.send(format!("спокій номер {i}")).unwrap();
        }
    });

    for msg in receiver {
        println!("отримано: {msg}");
    }
}
```

Відправник передає `sender` у потік, отримувач сам лишається в головному. Канал старається: отримані повідомлення приходять у порядку, а коли відправник завершує — отримувач відчуває кінець потоку і цикл завершується. Листування не потребує замків: ніхто нікому не заважає, поки не лізе у спільні дані.

## Вибір канала чи спільного дому

Що обрати — `Mutex` чи канал? Відповідь не технічна, а людська: якщо потоки ніби сусіди і час від часу треба «передати відповідь» — канал кращий. Якщо ж вони справді мусять постійно оновлювати один і той самий стан одразу — нехай буде замок.

Канал — це порядок без черг: кожен пише своє, ніхто не заглядає в чужий аркуш. Замок — це кімната для одного: щоб змінити — ввійди, зміни, вийди.

## Чотири слова безпеки

Якщо ти забудеш усі приклади, а запам'ятаєш одне — хай буде це. Rust-програма, яка зібралася, уже *в конкурентності безпечна*: у ній неможливий гон даних, коли два потоки одночасно правлять ту саму комірку без погодження; у ній неможлива передача небезпечного типу між потоками; у ній неможливо тримати спільні дані без `Mutex` або подібного. Це не обіцянки, а факт, який компілятор довів до запуску.

У світі, де складні системи падають саме через «дивні гонки», це величезний спокій: логіка може бути складною, але організація пам'яті — контрольована.

## Потоки легкі й важкі одночасно

Потік — найпростіша одиниця паралельної роботи, але й найцінніша. Він коштує пам'яті (стек, стан) і часу на перемикання, тож тисячі потоків — це вже тягар. Ось звідки в спільноті звичка: потік — для середньої кількості важких справ, а ось для тисяч легких очікувань — асинхронність (як ми бачили в шостій главі).

Потоки люблять «чисті» задачі, які вважають безперервно: перерахунок масивів, тяжкі обчислення, довгі цикли. Якщо твоя програма має один такий громіздкий шматок — віддай його окремому потоку, і решта програми заспіває паралельно.

```rust
use std::thread;

let handle = thread::spawn(|| {
    let mut sum = 0u64;
    for i in 1..=1_000_000 {
        sum += i;
    }
    sum
});

let result = handle.join().unwrap();
println!("{result}");
```

## Спільна пам'ять: читати, а не копіювати

Коли потоків кілька і вони читають одні й ті самі дані, копіювати все немає сенсу. Для цього Rust має позички `&T`, але позички не переживають потік — якщо значення може зникнути, поки інший потік читає. Тут на допомогу приходить `Arc`: «атомарний лічильник тримачів». Значення живе, доки хоч один тримач володіє ручкою.

```rust
use std::sync::Arc;
use std::thread;

let shared = Arc::new("спільний напис".to_string());

let a = Arc::clone(&shared);
let b = Arc::clone(&shared);

let h1 = thread::spawn(move || println!("{}", a));
let h2 = thread::spawn(move || println!("{}", b));
h1.join().unwrap();
h2.join().unwrap();
```

Кожен потік «взяв копію ручки на те саме значення». Коли востанній потік завершиться, лічильник спаде до нуля, і `String` піде зі сцени само. Ніхто нікого не залишає без домівки.

## Mutex і справедлива черга

Ми вже бачили `Mutex` у дії. Тепер додамо відтінок: коли два потоки чекають замок, хто отримає його першим? За замовчуванням — не гарантовано, але можна спостерігати, як черга не «морює» нікого голодом. У більшості задач цього достатньо: замок — інструмент взаємного виключення, а не скарбниця черг.

Зверни увагу на дві дрібниці з ранішим прикладом:

```rust
let mut guard = shared.lock().unwrap();  // замок
*guard += 1;                             // правка всередині
// guard падає тут, автоматично відпускаючи замок
```

`lock()` повертає `Result` (помилка, якщо той, хто тримав замок, «упав» у паніку). А справа у `guard`: коли вона йде зі сцени (кінець функції чи блоку), замок відпускається сам. Тобто ти не можеш «забути» замок — час життя поза межами гарантовано звільнить його. Це та сама турбота Rust про власність, тільки на вищому поверсі.

## Канали: більше двох співрозмовників

Ми бачили канал «один відправник — один отримувач». Але канали вміють і багатогранніші розмови. Один відправник може слати багатьом, або багато відправників — одному отримувачу. Класика: один отримувач збирає плоди з багатьох виробників.

```rust
use std::sync::mpsc::{Sender, channel};

fn worker(sender: Sender<u32>, id: u32) {
    sender.send(id * 2).unwrap();
}

fn main() {
    let (tx, rx) = channel();
    for id in 1..=4 {
        let tx = tx.clone();
        std::thread::spawn(move || worker(tx, id));
    }
    drop(tx); // усі копії відправників лишилися в потоках

    let sum: u32 = rx.iter().sum();
    println!("{sum}");
}
```

Ключова деталь — `let tx = tx.clone();` для кожного потоку і `drop(tx)` у головному: як тільки всі відправники (разом із копіями) завершаться, отримувач побачить кінець потоку. `rx.iter()` пройде рівно стільки повідомлень, скільки встигли надіслати. Порядок між потоками, звісно, довільний — але сума буде тією, якою й має бути.

## Атоми замість замків

Для найпростіших лічильників, які не потребують складної критичної секції, Rust має атомарні типи: `AtomicU32`, `AtomicBool` та інші. Їхня перевага — високі швидкості без блокування:

```rust
use std::sync::atomic::{AtomicU32, Ordering};
use std::sync::Arc;

let counter = Arc::new(AtomicU32::new(0));

for _ in 0..4 {
    let counter = Arc::clone(&counter);
    std::thread::spawn(move || {
        counter.fetch_add(1, Ordering::Relaxed);
    });
}
```

`fetch_add` — атомарне «додай і поверни попереднє». Лічильник не потребує замка, бо атомарні операції відбуваються «цілком або не відбуваються зовсім». Це легка зброя для простих станів, а важча («Mutex») — для складних.

## Send і Sync: перепустка в інший світ

Час підсумувати чарівні словутворення, бо вони пояснюють, чому Rust такий упевнений. `Send` — «можна передати іншому потоку», `Sync` — «можна позичити одночасно кільком потокам». Це не магічні закляття, а перепустки, які компілятор видає кожному типу.

- Перенести `Arc` між потоками — можна, бо `Arc` — `Send + Sync`.
- Перенести `&T` — можна, якщо `T: Sync` (тобто одночасні читачі безпечні).
- Перенести `MutexGuard` — можна, поки вона падає в тому ж потоці, де взяла замок.

Компілятор перевіряє перепустки на кожному кроці. Тому в Rust неможливі пересилки даних, які зламають потік: перепустки просто «не ті». Це найміцніший щит із тих, що ми зустрічали: він охороняє не окремий шматок коду, а цілу модель паралельності.

## Вправа на вечір: естафета через канал

Опиши собі маленьку естафету: головний потік слає число в канал, робітник множить його на два і відправляє назад іншим каналом, головний забирає результат. Це вправа на відчуття «листів» між домівками: хто в якій кімнаті, хто має який ключ.

Не квапся. Повтори в уяві з кількома робітниками: два робітники, два відповіді, одна збірна сума. Зрозумій, де потрібен `Arc` (спільний стан), а де — канали (обмін повідомленнями). Це рішення часто складніше за сам код — і саме воно стає справжнім умінням.

## Час життя у потоках: `'static` як перепустка

Коли ти `move`-передаєш дані в потік, компілятор часто вимагає, щоб вони жили `'static` — тобто не містили позичок на щось, що може зникнути, поки потік працює. Це не бюрократія, а гарантія: потік сам по собі — вільна домівка, і вона не повинна залежати від інших кімнат.

```rust
use std::thread;

fn main() {
    let text = String::from("перед сном");

    thread::spawn(move || {
        // text переїхало в потік — жодних позичок назовні
        println!("{text}");
    }).join().unwrap();
}
```

Усередині — `text` належить потоку. Він нічого не позичає назовні; усе володіє сам. Це і є відповідь, чому `'static` такий поширений у світі потоків: він гарантує «жодної запозиченої залежності».

## Патерн «виробник-споживач»

Одне з найпоширеніших застосувань потоків — патерн «виробник-споживач»: одні потоки створюють дані, інші їх обробляють. Канали виступають мостом між ними, і це дає дивовижну ясність.

```rust
use std::sync::mpsc::channel;

fn producer(tx: std::sync::mpsc::Sender<u32>) {
    for i in 0..5 {
        tx.send(i * i).unwrap();
    }
}

fn consumer(rx: std::sync::mpsc::Receiver<u32>) {
    for v in rx {
        println!("отримано {v}");
    }
}
```

Виробник не знає, коли саме з'їдять його плоди, а споживач не знає, звідки вони прийшли. Вони спілкуються про те, що важливо: «ось результат». Така розділеність — не формальність, а спосіб зменшити зв'язність програми.

## Падіння потоку: join і результат

Коли потік завершується, `join` повертає його результат. Якщо потік *упав* у паніку — `join` поверне помилку. Це важливо: твій код може дізнатися, що «той, хто пішов», не впорався, і ти вирішуєш, що з цим робити.

```rust
let handle = thread::spawn(|| {
    panic!("непередбачувано");
});

match handle.join() {
    Ok(_) => println!("усе добре"),
    Err(_) => println!("потік упав — але ми пережили"),
}
```

Стійкість — це вміння пережити падіння частин, не впавши цілком. `join` дає тобі саме це: спостереження за тим, що сталося, і можливість продовжити.

## Scoped потоки: короткий час життя

Інколи дані не `'static`, але потік живе недовго. Для таких випадків Rust має `thread::scope`, який дозволяє позичати дані і гарантує, що потоки завершаться, перш ніж дані зникнуть.

```rust
use std::thread;

let hello_world = "привіт";

thread::scope(|s| {
    s.spawn(|| println!("{hello_world}"));
    s.spawn(|| println!("{hello_world}"));
});
```

`scope` — це «обмежений гуртожиток»: дані позичаються, потоки виконуються, а коли блок завершується, усі потоки вже завершені. Це проявляє гнучкість Rust: не завжди потрібен `'static`; інколи досить «короткого» часу життя.

## Атоми та Ordering: мить, коли немає замка

Ми бачили `AtomicU32` із `Ordering::Relaxed`. Додамо ще трохи про ці «порядки». `Relaxed` — найм'якший: атомарна операція гарантує лише саму себе, без гарантій щодо інших змінних. Він найшвидший і підходить для простих лічильників.

```rust
use std::sync::atomic::{AtomicU64, Ordering};

let hits = AtomicU64::new(0);
hits.fetch_add(1, Ordering::Relaxed);
```

Для складніших сценаріїв є `Acquire` і `Release` — вони встановлюють «бар'єри пам'яті» між потоками. Не обов'язково продумувати всі деталі зараз; для базових лічильників `Relaxed` достатньо. Знайомство з цим словником допоможе впевненіше читати чужі паралельні програми.

## Потоки й володіння поза межами

Раніше ми побачили, що `move`-замикання «переселяє» значення в потік. Але що, як треба *кілька* потоків із тим самим значенням? Тоді виручає `Arc` (атомарний лічильник) разом із `Mutex` (замок) — вони разом утворюють класичну пару для спільного мутабельного стану.

```rust
use std::sync::{Arc, Mutex};

let state = Arc::new(Mutex::new(0i32));

let a = Arc::clone(&state);
let b = Arc::clone(&state);

std::thread::spawn(move || {     // a переїхав
    let mut g = a.lock().unwrap();
    *g += 1;
});
std::thread::spawn(move || {     // b переїхав
    let mut g = b.lock().unwrap();
    *g += 2;
});
```

Обидва потоки мають «ручку» на той самий `Mutex`. Кожен бере замок на мить, змінює, відпускає. `Arc` дозволяє поділити володіння, `Mutex` — забезпечити одне за одним. Це та сама надійність, що й із `Rc` + `RefCell` у однопоточному світі, тільки для потоків.

## Дедлоки: дві кімнати з замками

Класична пастка паралельності — *дедлок*: два потоки тримають по одному замку і чекають інший, так ніхто не може йти далі. Приклад простий, але він добре пояснює, чому порядок замків має значення.

```rust
// потік А тримає mut_a і чекає mut_b
// потік Б тримає mut_b і чекає mut_a
```

Щоб уникнути цього, досвідчені автори встановлюють єдиний «порядок» захоплення: завжди тримати спершу `mut_a`, а вже потім `mut_b`. Якщо обидва потоки дотримуються правила — дедлок неможливий. Rust не може автоматично вберегти від дедлоків (це не про типи), але він робить усе видимим, і автори свідомо обирають порядок.

## `Arc`: спільне володіння для потоків

Раніше ти бачив `Rc`, але `Rc` живе лише в одному потоці. Щоб безпечно поділитися володінням між потоками, існує `Arc` — атомарний лічильник посилань. Вона дозволяє кільком потокам тримати «посилання» на одне значення.

```rust
use std::sync::Arc;

let data = Arc::new(String::from("спільне"));
let t = std::thread::spawn({
    let d = Arc::clone(&data);
    move || println!("{}", d)
});
let _ = t.join();
```

`Arc::clone` не копіює вміст, а *збільшує лічильник*. Кожен потік тримає «ключ» до однієї домівки. Як тільки всі ключі використані, дім зникає. `Arc` — найкращий друг для читабельності спільних даних, які не змінюються.

## Повернення результатів із потоків

Ми бачили `join`, що чекає завершення. Корисно знати, що `join` повертає `Result` — результат роботи потоку, загорнутий у `Result`. Якщо потік злякався і панікував, ти дізнаєшся через `Err`.

```rust
let h = std::thread::spawn(|| 7 * 6);
match h.join() {
    Ok(v) => println!("відповідь: {v}"),
    Err(_) => println!("потік не завершився нормально"),
}
```

Це дає тобі можливість не «глухнути» на помилку потоку: ти ввічливо питаєш результат, а якщо його нема — ясно знаєш. Потоки, як і `Result`, говорять правду про свою долю навіть у момент завершення.

## Канали: черга повідомлень між потоками

Ми вже згадували `mpsc` («багато виробників, один споживач»). Воно — той м'який міст, через який потоки передають дані. Приймач `recv` чекає перше повідомлення, `try_recv` не чекає, а лише оглядає.

```rust
use std::sync::mpsc;
let (tx, rx) = mpsc::channel();
let _ = tx.send("привіт".to_string());
match rx.recv() {
    Ok(msg) => println!("отримано: {msg}"),
    Err(_) => println!("канал закрито"),
}
```

Канал — це «поштова скринька»: виробники кладуть листи, споживач забирає. Такі мости розводять потоки між «ролью дописувача» і «ролью читача», і це набагато безпечніше за прямі спільні масиви.

## Медитація на ніч

Сьогодні ми познайомилися з руками, яких багато: потоками, замками, каналами. Ми дізналися, що Rust не просто радить бути обережним, а будує безпеку в свою природу — і тому конкурентність тут не лякає, а дозволяє.

Уявімо кухню, де кілька кухарів працюють одночасно: кожен біля свого вогню, кожен має власний ніж, а спільні інгредієнти передаються з рук у руки по черзі. Це і є програмна конкурентність — спокійна, чесна, діловита.

> Хто хоче спільного — бере замок,
