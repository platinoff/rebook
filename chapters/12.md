## Господар дому

У будь-якому серйозному проєкті на Rust є невидимий господар: не компілятор, а помічник, який керує всім господарським життям. Звати його Cargo. Він знає, де лежать джерела, які залежності потрібні, як зібрати проєкт, як прогнати тести, як викласти його до світу.

Ми вже бачили його на початку книги: `cargo new den`, `cargo run`. Зараз дивимось ближче, бо розуміння Cargo — це розуміння того, як Rust-спільнота живе разом.

## Що народжує cargo new

Коли ти пишеш `cargo new name`, Cargo створює маленький дім:

```text
name/
├── Cargo.toml
└── src/
    └── main.rs
```

У `Cargo.toml` — паспорт проєкту: ім'я, версія, опис, список залежностей. У `src/main.rs` — початок основної програми. Розгляньмо паспорт ближче:

```toml
[package]
name = "den"
version = "0.1.0"
edition = "2021"

[dependencies]
```

`edition` — це «діалект» мови: з яким поколінням Rust ми говоримо. Версія — це твій етап життя проєкту: `0.1.0` — скромний початок. А список залежностей — це запрошення інших домів до співпраці.

## Один дім, багато кімнат

Rust розрізняє два головні типи проєктів. Бібліотека — це дім-ресурс: вона не запускається сама, а служить іншим (вона описує, «як можна працювати»). Бінарник — це дім-програма: вона запускається і робить справу.

Усередині одного проєкту можуть жити разом: бібліотека в `src/lib.rs` і кілька бінарників у `src/bin/`. Це зручно, коли ти хочеш зібрати в одному домі і спільну логіку, і кілька програм, які нею користуються.

## Де живе спільнота: crates.io

Крейти — це готові будинки, які ти можеш запросити до свого проєкту: не будувати з нуля обробку мережі чи серіалізацію, а покликати перевірені, спільно підтримувані. Головний ринок — `crates.io`. Щоб запросити крейт, ти просто додаєш рядок у `Cargo.toml`:

```toml
[dependencies]
serde = { version = "1", features = ["derive"] }
tokio = { version = "1", features = ["full"] }
```

Рядок `serde = ...` — це запрошення. Cargo піде на ринок, знайде найсвіжішу згоду, завантажить і підготує. Іноді обрані крейти приносять і свої залежності — це природно: гість приводить друзів, і розмір дому власника враховує їх усіх.

## Документ, зрозумілий усім

Успішний крейт — це не лише код, а й розповідь про себе. Rust має вбудований генератор документації: пиши в `///` і отримуєш тихий, красивий веб-сайт, зібраний з цих коментарів. Команда `cargo doc` створює локальну документацію, а `cargo doc --open` відкриває її в браузері.

```rust
/// Рахує кількість спокійних слів у рядку.
pub fn calm_words(text: &str) -> usize {
    text.split_whitespace().count()
}
```

Документація — це подарунок майбутньому собі та іншим: ти завжди знаєш, чому написав те, що написав, а читач не блукає в чужих думках. Коментарі — це ввічливість у спільному домі.

## Профілі: debug і release

Cargo має два обличчя для збірки. `cargo build` (або `cargo run`) — це *debug*: швидко, з багатими даними для налагодження, але повільно. `cargo build --release` — це *release*: компілятор напружується довше, оптимізує все, що може, і віддає швидку програму.

Різницю видно з перших секунд:

```text
cargo build          # майже миттєво
cargo build --release   # довше, але результат — швидкий бігун
```

Це як готувати їжу: швидко — це сирі інгредієнти з ложки, а по-справжньому — це повільний вогонь, що розкриває смак. Для іграшок — debug, для світу — release.

## Тести як домашня звичка

Cargo керує також і тестами: `cargo test` знаходить усі тести в проєкті, збирає їх і проганяє один за одним, повідомляючи про кожен результат. Про тести докладно поговоримо в наступній главі; тут згадаймо лише, що Cargo — їхній господар і друг.

А ще Cargo вміє перевіряти, чи програма збирається, не збираючи: `cargo check` згодовує компілятору тільки синтаксис та типи — найшвидший спосіб впевнитись, що в домі порядок.

## Нічний сторож: clippy

Спільнота Rust має ще одного друга, і звуть його `cargo clippy`. Це не просто компілятор, а *доброзичливий критик*: він переглядає твій стиль і підказує, як написати чистіше, швидше, зрозуміліше. Він не сварить за помилки — він ділиться досвідом.

```text
cargo clippy --all-targets
```

Звичай у спільноті такий: перед тим як завершити, глянь, що скаже clippy. Він прощає все, але його поради роблять код кращим. Це як наставляння від старшого товариша в тихій вечірній годині.

## Версії та семантичне версіювання

Час зазирнути у версії, бо вони — найважливіша мова, якою розмовляють крейти. Кожен крейт має номер вигляду `1.2.3`. Перша цифра — «мажорна» версія: коли вона міняється, можуть змінюватися (і ламатися) речі. Друга — «мінорна»: додають нове, не ламаючи старого. Третя — «патчева»: виправляють дрібні помилки.

```toml
[dependencies]
serde = { version = "1", features = ["derive"] }
```

Рядок `version = "1"` означає «бери будь-яку 1.x.y — у межах сучасних обіцянок». Можна вказати точніші: `"^1.2"` — «від 1.2 до 2.0», `"1.2"` — «дуже близько до 1.2». Ця система — домовленість усього світу крейтів: вона дозволяє всім бути впевненими, що оновлення не розламає дім.

## Cargo.lock: книга точних версій

Коли Cargo вперше збирає проєкт, він створює файл `Cargo.lock`: повний реєстр точних версій усіх залежностей — хто з ким і в якій комбінації. Для бібліотек цей файл зазвичай ігнорують, а для програм — навпаки, зберігають у git.

```text
[[package]]
name = "den"
version = "0.1.0"
dependencies = ["serde"]
```

Зберігаючи `Cargo.lock`, ти гарантуєш: кожен, хто збирає твою програму (ти сам через півроку, колега на іншому комп'ютері), отримує *ті самі* версії залежностей. Жодних «а чому в мене інша поведінка, адже код однаковий?». Передбачуваність, яка варта рядка в git.

## Workspaces: дім з кількома кімнатами

Великий проєкт часто живе як «workspace» — робочий простір, у якому кілька крейтів діляться одним Cargo.lock і збираються разом. Уяви дім, де бібліотека «логіка», крейт «конфігурація» і бінарник «застосунок» — окремі кімнати, але під одним дахом.

```toml
[workspace]
members = ["logic", "config", "app"]
```

Спільний Cargo.lock у такому домі — спільний фундамент: усі кімнати користуються одними тими ж версіями залежностей, і перегляд оновлень відбувається один раз. Якщо проект росте з десяти файлів у сотні — workspace стає не розкішшю, а нормальним способом жити.

## cargo add, cargo update, cargo outdated

Екосистема має численні зручні команди, які полегшують життя з метаданими. `cargo add tokio` — додасть залежність прямо з командної строки і догляне `Cargo.toml`. `cargo update` — оновить версії в межах дозволеного. Зовнішні утиліти, як `cargo outdated`, підкажуть, які крейти відстали. Не все це треба вчити сьогодні — але знати, що інструменти існують, приємно.

## Крейт: більше ніж код

Успішний крейт — це не лише імпортовані функції. Це крихітна «особистість» з ім'ям, описом, ліцензією і документацією. Ось фрагмент `Cargo.toml` з усіма обов'язковими атрибутами:

```toml
[package]
name = "night-sky"
version = "0.1.0"
authors = ["Artem Platinov"]
description = "Мале утилітне поле для зображення нічного неба"
license = "MIT"
```

Ліцензія — важлива частина поваги до інших: вона говорить, чий це дім і на яких умовах дозволений вхід. Перед випуском крейта в світ (`cargo publish`) саме вона має бути в порядку. Так живуть тисячі крейтів — з іменем, репутацією і законами.

## Дотична документація: doctests

Ще один подарунок системи документації — *доктести*: приклади в `///`-коментарях можуть ставати тестами. Cargo перевіряє, чи приклад справді «працює». Це магія, яка тішитиме ще в главі про тестування.

```rust
/// Додає два числа.
///
/// ```
/// let result = add(2, 2);
/// assert_eq!(result, 4);
/// ```
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}
```

Коли хтось читає документацію, він бачить приклад, і може його виконати в себе; коли ти запускаєш `cargo test`, цей приклад тестується. Один камінь — два скарби: пояснення й перевірка.

## Нічна розмова з cargo

Уся книга, ми тримали Cargo як господаря дому. Але варто ще раз закріпити «нічний» набір команд — тих, що супроводять кожен вечір коду. Ось твій зручний карманний листок:

```text
cargo new    name      # заснувати новий дім
cargo build            # зібрати проєкт (debug)
cargo build --release  # зібрати для світу
cargo run              # зібрати і запустити
cargo test             # прогнати тести
cargo check            # швидка перевірка типів
cargo doc --open       # збір документації
cargo clippy           # доброзичлива порада
```

Це мінімум, який покриває майже все життя проєкту. Не заучуй напам'ять: досить знати, що список існує і що він не страшний. Так само, як удома знання «де шафа» — ти не перечитуєш увесь будинок щоранку.

## Розуміння повідомлень Cargo

Інколи Cargo друкує дивні рядки про «downloads», «compiling», «Finished». Розшифруємо тих, кого він показує найчастіше:

- `Downloading` — вперше тягне новий крейт із реєстру.
- `Compiling` — перекладає крейт мовою машини; перший раз завжди найдовший.
- `Finished` — зібраний, усе добре.
- `warning: unused...` — можливо, ти забув скористатися чимось; не шкодуй часу — заглянь.
- `error: ...` — зупинка з причиною; дивись на кінцівку повідомлення, там найточніша вказівка.

Інколи Cargo оновлює реєстр («Updating crates.io index») — це мережева дія, яка за перший раз може бути повільна. Без паніки: індекс він уже знає, наступні рази швидші.

## Feature-прапорці: модульність крейтів

Багато великих крейтів — не «моноліт», а набір частин, які вмикаються прапорцями-features. Наприклад, у `tokio` ти можеш увімкнути лише той модуль, який потрібен:

```toml
[dependencies]
tokio = { version = "1", features = ["rt-multi-thread", "macros", "time"] }
```

Така модульність — повага до дому: не тягни в проєкт усе, коли потрібне мале. Спільність Rust у кращому вигляді: крейт дозволяє контролювати, скільки світу ти береш із собою. Це ще й пришвидшує збірку.

## `cfg`-вимоги: цікаві умови

Часом код має поводитися гнучкіше залежно від середовища. Rust має механізм умовної компіляції:

```rust
#[cfg(target_os = "windows")]
fn default_font() -> &'static str { "у Windows — Segoe UI" }

#[cfg(target_os = "linux")]
fn default_font() -> &'static str { "у Linux — DejaVu" }
```

Це не «дивний код для ускладнення», а здатність дому підлаштовуватися. Бібліотеки користуються цим, щоб один крейт мирно жив на різних системах. Якщо коли-небудь побачиш `#[cfg(...)]` — знай: це «двері для одних, а не для всіх».

## Мережа залежностей та «дерево»

`cargo tree` показує, хто від кого залежить:

```text
serde v1.0
└── serde_derive v1.0
    └── syn v2.0
```

Це «дерево» твого дому: зрозуміти, хто кого кличе, — перший крок до впевненого контролю. Не лякайся розміру дерева; чому бути десяткам крейтів, коли вони задовольняють прості потреби.

## `--release`: коли потрібна швидкість

`cargo build` збирає проєкт у «debug»-режимі: швидко, з багатою інформацією для налагодження, але не з найбільшою швидкістю. А `cargo build --release` вмикає оптимізації: код стає швидшим, але збірка повільніша. Для програм, які ти випускаєш у світ, `--release` — правильний вибір.

Різниця іноді вражає: програма, яка в debug працює кілька секунд, у release одразу. Це не магія — це мова, що витрачає трохи часу, аби збірка була «заточеною». Звикай: для повсякденної розробки — `cargo run`, для готового результату — `cargo build --release`.

## Профілі: тіні `Cargo.toml`

За кілька років практики ти, можливо, захочеш налаштувати, як саме збирається проєкт — наприклад, додати оптимізації в debug або вказати рівень. Для цього в `Cargo.toml` є секції `[profile.dev]`, `[profile.release]` та інші.

```toml
[profile.release]
opt-level = 3
lto = true
```

Не турбуйся зараз про всі прапорці — їх досить просто знати, що вони існують. Це ще один спосіб, як Cargo поважає дом: він дає тобі контроль над тим, скільки часу й сил витрачати на збірку, а скільки — на швидкість результату.

## Бібліотека чи виконувана програма?

У `Cargo.toml` може бути ще один вибір: чи твій проєкт — просто «виконувана програма» (binary), чи «бібліотека» (lib), яку інші можуть підключати. Часто проєкт має і те, і інше: `lib.rs` для публічних функцій, `main.rs` — для входу.

```toml
[lib]
name = "night_sky"
```

Таке розділення допомагає бібліотеці залишатися чистим API, а бінарнику — бути інтерфейсом. Не поспішай розділяти одразу; коли побачиш, що функції повторюються в кількох програмах, — винеси їх у `lib`.

## Крейти, які змінюють правила гри

Світ крейтів величезний, але кілька з них ти зустрінеш у багатьох проєктах: `serde` (серіалізація), `anyhow` і `thiserror` (м'які помилки), `clap` (розбір CLI-аргументів), `rayon` (паралелізм), `tokio` (асинхронність), `log` + `env_logger` (журналювання). Це не «обов'язковий список», а орієнтир: коли в тебе виникне природна потреба, ти зможеш згадати «а, для цього є крейт».

Не заучуй їх усі наперед. Досить знати поіменно кілька, щоб у потрібний момент зробити пошук. Світ крейтів — не список іспиту, а шафа з добрими інструментами: відкриваєш тоді, коли прийшла пора.

## `cargo doc`: документація поруч

Rust має вбудовану здатність будувати документацію з `///`-коментарів. `cargo doc` створює зрозумілі HTML-сторінки для твого проєкту та всіх залежностей, а `cargo doc --open` одразу відчиняє їх у браузері.

```text
cargo doc --open
```

Це не «приємна прикраса», а цінний інструмент навчання: ти гортаєш документацію до крейта, бачиш його методи, сигнатури, приклади. Коли сумніваєшся, як користуватися функцією, — `cargo doc --open` і пошук. Документація, зібрана з доглянутих коментарів, перетворює сайт на твого терпеливого вчителя.

## Версії та їх важливість для збірки

Ми вже торкалися версій; додамо відтінок про те, чому "точність" така цінна. Коли `Cargo.toml` каже `"1.2"`, це не «дозвіл на будь-що», а «межа сумісності». Якщо оновлення доведе версію до `2.0`, Cargo зупиниться і спитає. Це захист твого дому від незапланованих змін.

Система не ідеальна, але чесна: вона заохочує розробників крейтів дотримуватися обіцянок семантики версій. Тому й можна спати спокійно: оновлення патчевого номера не зламає збірку без повідомлення.

## Залежність як запрошення, а не ярмо

Великий урок цієї глави: залежності — це запрошені гості, а не обов'язкові утриманці. Ти можеш відкрити `Cargo.toml` і спокійно «відпустити» крейт, який більше не потрібен, видаливши рядок із `dependencies`. Cargo одразу перестане тягти його при наступній збірці.

Ця свобода — частина філософії «менше шуму». Якщо проєкт росте, перевір час від часу, які гості вже «пішли», а які лишилися лише для примхи. Дім стає охайнішим, а збірка — швидшою.

## `cargo fmt`: єдиний почерк

Rust має офіційний «каліграф» — `cargo fmt`. Він автоматично вирівнює відступи, розставляє розділові та приводить код до єдиного стилю. Можливо, ти ще не думаєш про це, але це приємна звичка.

```text
cargo fmt
```

Значення `fmt` не лише в естетиці: коли вся команда користується одним форматом, злиття стає чистішим, а розв'язки у дифах — меншими. «Чий почерк» не обговорюється — є один. Це дає спокій: тобі не треба вигадувати форму; інструмент знає її за тебе.

## Вектори версій і `cargo update` на практиці

Коли з'являється бажання оновити залежності, `cargo update` дозволяє рухатися в межах дозволеного. Після нього `Cargo.lock` перепише точні версії. Якщо щось зламалось — `Cargo.lock` колишній ти повертаєш назад, і збірка стабільна.

```text
cargo update          # оновить у межах дозволу
```

Це цикл «обереждності»: спершу подивись, що змінилося, потім виріши, чи лишати. Не поспішай оновлювати все одразу; оновлюй усвідомлено, кілька крейтів за раз. Передбачуваність залежностей — надійний партнер ночі.

## Після `cargo new`: перші кроки у новому домі

Коли `cargo new` створює проєкт, ти вже маєш `src/main.rs`, `Cargo.toml` і порожній git (якщо просив). Що робити далі? Не обов'язково занурюватися в тонкощі; почни з найпростішого:

1. Відкрий `src/main.rs` і зміни рядок друку на свій.
2. `cargo run` — побач результат.
3. Додай кілька функцій і виклич їх.
4. Коли захочеш тестів — додай `#[test]` і `cargo test`.

Ці кроки прості, але вони — перші «будівельні блоки» твого дому. Не ускладнюй собі старт; Cargo вже прибрав для тебе зайві перешкоди на шляху до чистого аркуша.
