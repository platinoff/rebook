## Життя посеред посилань

У попередній главі ми познайомились із тим, що посилання — це гості, які приходять подивитися. Але є в гостей одна властивість, про яку варто говорити окремо: вони не вічні. Посилання має жити доти, доки живе те, на що воно вказує. Rust стежить за цим так пильно, що це навіть отримало спеціальне ім'я — *час життя*, lifetime.

Не лякайся цих слів. Час життя — це просто те, скільки ще існуватиме значення, на яке ми дивимося. Ідея набагато простіша, ніж синтаксис, який її виражає.

## Чому посилання не може бути вічним

Уяви папірець із записом, який лежить на столі. Хтось приклеїв на нього стрілку-покажчик: «сюди дивись». Поки папірець на столі — все добре. Але уяви, що папірець викинули, а стрілка залишилась — і тепер вона вказує на місце, де нічого немає. Людина, що прийде й подивиться, здивується. Або, гірше, знайде на тому місці щось зовсім інше.

Це називається *висячим посиланням* — dangling reference. У мовах, що не стежать за цим, такі випадки стають джерелом дивних помилок, які з'являються лише час від часу. Rust робить найкраще з можливого: забороняє висячі посилання *ще на етапі компіляції*.

```rust
fn bad() -> &String {
    let local = String::from("недовговічне");
    &local // компілятор зупинить: local помре разом з функцією
}
```

Компілятор не дасть зібрати таку функцію. Зауваж: він не питає, чи повернення буде використане. Він дивиться на сам факт: значення, на яке посилаються, не переживе функцію — отже, посилатися на нього назовні не можна. Суворий і добрий одночасно.

## Як повертати посилання безпечно

Щоб повернути посилання, потрібно, щоб воно вказувало на щось, що переживе функцію. Найчастіше — на аргумент, який прийшов у функцію:

```rust
fn first_word(text: &str) -> &str {
    match text.find(' ') {
        Some(space) => &text[..space],
        None => text,
    }
}

fn main() {
    let sentence = String::from("тиша приходить ввечері");
    let word = first_word(&sentence);
    println!("перше слово: {word}");
}
```

Тут `first_word` приймає `&str` і повертає `&str`. І Rust пов'язує повернуті посилання з вхідними: функція може повернути лише те, що живе стільки ж, скільки її вхід. Завдяки цьому головне правило стає безпечним: поки живе `sentence`, живе і `word`.

## Стрілки на папірцях, яких не видно

У коді інколи трапляються позначки `'a`, `'b`, `'static` — і вони виглядають як чужоземні слова. Це як імена періодів, якими компілятор описує відношення між часом існування посилань.

Роздивись приклад: функцію, яка обирає більший із двох текстових фрагментів, не забираючи жодного:

```rust
fn longer<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() >= y.len() { x } else { y }
}
```

Тут `'a` — це обіцянка: «те, що я повертаю, житиме стільки ж, скільки обидва аргументи». Апостроф не мусить лякати: це просто коротке ім'я проміжку часу. Компілятор сам показав би його мені в поясненнях, навіть якби я одного дня вирішив, що воно йому не потрібне.

## Мовчазне життя

Приємна новина: у звичайному коді ти найчастіше взагалі не пишеш позначок часу життя. Rust сам зможе вивести співвідношення, якщо воно просте:

- коли функція приймає одне посилання і повертає одне, компілятор додумає сам (це називають правилом елізії, воно як правило ввічливості: не обов'язково вимовляти очевидне вголос);
- коли методи повертають посилання на поле `self`, Rust також сам розуміє, що посилання пов'язане з життям об'єкта.

Тобто до позначення `'a` ми звертаємося лише тоді, коли функція приймає кілька посилань і має пояснити, яке саме вона повертає. Це рідкість, а не норма.

## Рядки: чиї вони

Настав час упорядкувати два дружніх типи: `&str` і `String`.

`&str` — це погляд на частину тексту, якою володіє хтось інший. Ми можемо розглядати його, різати на фрагменти, порівнювати — але не змінювати. Він дешевий: це лише вказівник і довжина.

`String` — це текст, яким ми володіємо. Він може рости, мінятися, і в кінці звільниться сам, коли власник завершить роботу.

```rust
fn main() {
    let owner = String::from("крапля роси");  // володіємо текстом
    let view: &str = &owner[0..6];             // дивимось на "крапля"
    let part: &str = "суха частина";          // літерал живе завжди
    println!("{view} … {part}");
}
```

Рядкові літерали, як-от `"суха частина"`, мають особливий час життя, що позначається `'static`: вони вшиті в саму програму й живуть від початку до кінця. Це посилання, які не бояться часу.

## Друзі, які ніколи не конфліктують

Поеднаємо дві важливі речі з цілої попередньої глави: власність і позики. Правила, які Rust перевіряє щоразу, коли ти користуєшся змінною, можна перелічити по пальцях:

- у кожного значення один власник у будь-який момент;
- поки значення живе, посилань на нього можна мати скільки завгодно — якщо вони читають;
- писати (через `&mut`) можна тоді, коли ніхто інший на це значення більше не дивиться;
- посилання ніколи не переживає своє значення.

Ці чотири правила звучать сухо, але насправді вони — як чотири стовпи, на яких стоїть цілий тихий дім. Якщо програма в Rust скомпілювалася — три з чотирьох страшилок про пам'ять уже не можливі в ній взагалі.

## Час життя і справжнє життя

Іноді варто зробити крок назад і подивитися на ці механізми без компіляції. Часи життя — це чесне визнання того, що все в світі існує лише до певної миті, і що мудрість полягає не в тому, щоб заперечувати кінець, а в тому, щоб організувати життя так, щоб ніхто не спирався на те, що вже пішло.

Rust, мова, яка іноді здається найтехнічнішою з усіх, насправді навчає дуже людяної мудрості: не тримайся за те, чого вже немає; не обіцяй того, що не переживе твоїх слів; дай кожній речі жити свій строк і звільнитись без шуму.

## Правила часу життя на пальцях

Хоч тема зветься мудро, саме знання можна укласти в кілька рядків. Сформулюємо їх у звичайних словах, перш ніж вирушимо глибше:

1. Кожне посилання живе не довше, ніж значення, на яке воно вказує.
2. Якщо функція приймає одне посилання і повертає одне — компілятор сам може здогадатися про зв'язок (елізія).
3. Якщо функція приймає кілька посилань — доведеться пояснити, з яким саме пов'язане повернене.
4. Літеральні рядки мають особливий, «вічний» час життя `'static`.

Ці правила — не догма, а переказ того, як компілятор розуміє світ. Вони з першого погляду можуть здаватись хитрими, але на практиці у восьми випадках із десяти ти взагалі не напишеш жодної літери часу життя. Компілятор сам направить логіку: де треба, він скаже прямо «тут потрібно `<'_>`».

## Чому компілятор такий суворий

Хтось питає: а чи не можна було б обійтися без цього? В інших мовах програма сама «здогадується», де що живе, і все одно щось ламається. Rust пішов іншим шляхом: не обіцяй дива, а перевір факти.

Причина в тому, що висячі посилання — джерело гірших помилок у системному програмуванні. Вони поводяться дивно: працюють роками, а потім вибухають на чужому компіляторі, в іншій збірці, з іншими даними. Rust визначив, що це занадто дорого для спокою, і зробив висячі посилання просто неможливими: компілятор доводить, що код безпечний, ще до його запуску.

Це не ворожість до програміста, а дружба з майбутнім: ти можеш спати спокійно, знаючи, що за дверима не чекає «збій, який не можна відтворити».

## Елізія: очевидне, не промовлене

Зустрінемося з «мовчазним» правилом ближче. Ось функція, у якій жодної літери часу життя немає, але компілятор усе розуміє:

```rust
fn longest(a: &str, b: &str) -> &str {
    if a.len() >= b.len() { a } else { b }
}
```

Стоп, тут є підступ: функція приймає *дві* позички. Чи зможе компілятор сам зрозуміти зв'язок? У випадку з двома входами — ні, і він скаже про це. У випадку з *одним* входом — так:

```rust
fn first_half(s: &str) -> &str {
    &s[..s.len() / 2]
}
```

Один вхід, один вихід: Rust без зайвих слів пов'язує їх. Така елізія — не магія, а ввічливість мови: коли можливості не гадати, мова не гадає. Вона зберігає енергію для справді складних кутів.

## Якщо дві позички: намалюй зв'язок

Повернімося до `longest`. Щоб допомогти компілятору, ми маємо сказати: «повертаю той, що живе не менше за обох». Пишемо букву часу:

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() >= y.len() { x } else { y }
}
```

`'a` — це ім'я періоду, який треба розуміти так: «обери спільний часовий проміжок, що належить і x, і y, і поверни посилання, яке в ньому живе». Компілятор дивиться, скільки живуть виклики:

```rust
let short = String::from("коротке");
let long = String::from("найдовший рядок");
let result = longest(&short, &long);
```

`result` отримає час життя коротшого з двох — бо обіцяти більше не можна. Це як домовленість: «я не пообіцяю тобі те, що може зникнути раніше». Усе чесно, усе виміряно, усе спокійно.

## Структура з позичками

Часи життя з'являються не лише в функціях, а й у типах. Якщо структура тримає посилання, вона має сказати, як довго воно житиме:

```rust
struct Reading<'a> {
    text: &'a str,
    note: usize,
}

fn main() {
    let source = String::from("вечірня сторінка");
    let reading = Reading { text: &source, note: 2 };
    drop(source);
    // println!("{}", reading.text); // неможливо: source пішло
    println!("{}", reading.note);
}
```

Структура `Reading<'a>` — це «тримач позички», який повинен жити не довше за самого позиченого. Коли `source` зник, `reading.text` втратив фундамент — і компілятор не дасть нам до нього зазирнути. Число `note` при цьому живе спокійно: воно належить самій структурі.

Це не складно, а обов'язково: так Rust дбає, щоб усі тримачі позичок вмирали не пізніше за своїх боржників. Маячня? Ні — сердечність.

## Статична позичка: живе майже вічно

Серед часів життя є одна особливість: `'static`. Він позначає «стільки, скільки живе сама програма». Це про рядкові літерали:

```rust
fn name() -> &'static str {
    "Кассіопея"
}
```

`"Кассіопея"` вшита в бінарник, і вона з тобою від запуску до завершення програми. Акцно, цей час життя — не магія: просто текст, який лежить разом із кодом і нікуди не дівається.

Коли бачиш `&'static str`, знай: це або літерал, або значення, якому гарантовано жити довго. Усе інше — залежить від контексту, і компілятор наполягатиме на чесності.

## Трюки зі зрізами рядків

Позички рядків особливо приємно використовувати для «зрізів» — фрагментів тексту без копіювання:

```rust
let phrase = String::from("тиша у вечорі");
let space = phrase.find(' ').unwrap_or(0);
let first_word = &phrase[..space];
let rest = &phrase[space + 1..];

println!("перше слово: {first_word}");
println!("решта: {rest}");
```

`&phrase[..space]` — це позичка на частину тексту: нульового копіювання, один погляд. Розрізання не забирає рядок, не плодить копії — лише визначає вікна, якими дивимося. Це потужно й легковажливо водночас: система часу життя гарантує, що вікна існують лише поки живе текст.

Позички-зрізи — як ліхтар у книзі: він освітлює сторінку, не вириваючи її.

## Вправа на сьогодні

Спробуй у тихий момент самостійно «споткнутися» про час життя: напиши функцію, яка приймає `&str`, повертає `&str`, а всередині випадково намагається повернути щось локальне. Подивися, яке повідомлення напише компілятор. Звичайно, згодом виправ: або позичся аргументом, або поверни `String` у володіння.

Такий ритуал — «зламай свідомо, побач, як це виглядає» — один із найкращих способів звикнути до думки, що компілятор не проти тебе, а просто мудрий опікун. Ти вже зрозумів: час життя не обмежує — він захищає.

## Структури з методами

Структури — не просто контейнери даних; вони можуть нести й *поведінку*. Власна компанія даних і методів, які з ними працюють, — це звичний осередок у Rust. Метод оголошується в блоці `impl`, і він завжди має доступ до себе через `self`.

```rust
struct Book {
    title: String,
    pages: u32,
}

impl Book {
    fn pages_per_night(&self, nights: u32) -> u32 {
        self.pages / nights
    }
}
```

`&self` — це позичка: метод *читає* структуру, не забираючи її. Тому ти можеш викликати метод хоч десять разів поспіль, і дані залишаться цілими. Ось різниця між «читачем» і «власником»: читач приходить, дивиться, іде; власник тримає ключі.

## Позички мутабельні чи неменяться

У Rust дві категорії позичок, і це пояснює, чому код поводиться так м'яко. `&T` — це «погляд, що не змінює». `&mut T` — це «рука, яка має право змінювати». Правило просте, але могутнє: *ти не можеш позичити мутабельно, якщо вже є активна незмінна позичка на те саме значення.*

```rust
fn main() {
    let mut count = 10;

    let reader = &count;      // незмінна позичка
    println!("{reader}");

    // let writer = &mut count;  // помилка: уже є reader

    println!("{count}");
}
```

Чому так? Бо якщо б ти міг змінити `count`, поки хтось читає, читач міг би побачити серединне, нерозсудливе значення. Rust блокує це наперед. Результат — спокій: позички не змагаються.

## Час життя: невидимі межі останнього погляду

Час життя (`'a`) — це «межа, скільки живе позичка». Компілятор не завжди показує їх у твоєму коді, бо часто може зрозуміти сам. Але коли функція приймає позички і повертає позичку, він запитує: «до чого саме ти хочеш досилати?»

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

Тут `'a` — це «одна і та сама межа життя» для обох входів і виходу: те, що повертається, живе доти, доки живі обидва входи. Це не складна арифметика; це спосіб сказати «я повертаю одну з двох позичок, тож вона може жити, поки вони живі».

## Статичний час життя: `'static`

Є особлива межа — `'static`, яка означає «живе все життя програми». Рядкові літерали (`"слово"`) — це `&'static str`, бо вони вшиті в саму програму.

```rust
fn greeting() -> &'static str {
    "спокійної ночі"
}
```

`'static` — це не магія, а окремий випадок: значення нікуди не зникає. Тому позички-літерали можна так спокійно повертати з функцій — вони існують стільки, скільки сама програма.

## Зрізи: погляд на частину без копії

Зріз (`&[T]` для векторів, `&str` для рядків) — це «вікно» на частину колекції. Він не копіює дані; він просто вказує на початок і довжину. Це економно і безпечно: зріз знає свої межі і не дасть прочитати те, чого нема.

```rust
fn first_word(s: &str) -> &str {
    &s[..s.find(' ').unwrap_or(s.len())]
}

fn main() {
    let phrase = "тиша навколо";
    let word = first_word(&phrase);
    println!("{word}");
}
```

Зрізи — це природний спосіб поділу даних без копіювання. Вони передаються посиланням, живуть у межах часу життя, і це знову повертає нас до теми власності: даних не розмножують, їх позичають очима.

## Вправа на вечір

Опиши структуру `Room` з полями `name: String` і `lights: u8`. Додай метод `switch_on(&mut self)`, який збільшує `lights` на 1, і метод `is_lit(&self)`, який повертає `bool`. Використай обидва методи послідовно в `main` — і зверни увагу, де потрібна мутабельна позичка, а де ні. Це вечірня вправа на відчуття: читач проти власника.

## Статичні екземпляри: краще, ніж копії

Часом хочеться мати кілька примірників однієї структури, але не дублювати поля вручну. Rust має `Default` — трейт, що дає «типове» значення типу, а також можна описати свій метод `new`, який повертає новий екземпляр за замовчуванням.

```rust
struct Room {
    name: String,
    lights: u8,
}

impl Room {
    fn new(name: &str) -> Room {
        Room {
            name: name.to_string(),
            lights: 0,
        }
    }
}
```

Звичка робити `new` — одна з найпоширеніших серед авторів Rust. Вона робить початок зрозумілим: «дивлячись на `Room::new(...)`, я знаю, що саме створюється». Це маленька турбота, яка рятує від плутанини з полями.

## Унарні методи та власність

Методи структури бувають не лише «читачі» (`&self`) і «змінювачі» (`&mut self`) — буває і «поглинач» (`self` без `&`). Такий метод *приймає володіння* екземпляром і зазвичай перетворює його в щось нове.

```rust
impl Room {
    fn final_night(self) -> String {
        format!("{} кімната: {} світла", self.name, self.lights)
    }
}
```

Після виклику `room.final_night()` змінна `room` більше не відкривається: метод забрав володіння. Це не покарання, а стиль: ти кажеш «ця структура призначена для одноразового перетворення». Такий патерн любить ланцюжок перетворень, де кожен крок «з'їдає» попередній.

## Суміш володіння та позички в аргументах

Методи теж можуть приймати аргументи — і тут працюють усі правила власності, які ми вже знаємо з функцій. Відмінність лише в тому, що є `self`-параметр, який приходить першим (і саме він належить до об'єкта).

```rust
impl Room {
    fn compare(&self, other: &Room) -> bool {
        self.lights > other.lights
    }
}
```

Тут обидва — позички (`&self`, `&other`): метод лише порівнює, нічого не забираючи. Це чисте читання. Якби ми передали `other` без `&` — ми б перемістили другу кімнату в метод. Вибір між позичкою та переміщенням — щоденна увага автора Rust, і вона стає автоматичною з практикою.

## Вправи глибше: стан і зміни

Коли ти станеш упевненішим, спробуй ускладнити вчорашню вправу `Room`: додай поле `color` (рядок) і метод `paint(&mut self, color: &str)`, який змінює його. Зроби так, щоб після фарби ти міг прочитати новий колір. Це вправа на відчуття: позичка `&mut` відчиняє для зміни, але ти не можеш читати, поки змінюєш. Тонка межа, яку Rust робить видимою.

## Медитація на ніч

Сьогодні ми дізналися, що посилання мають час життя, що воно найчастіше приховане й мовчазне, що `&str` дивиться, а `String` володіє, і що висяче посилання неможливе в Rust.

Не намагайся запам'ятати кожну деталь. Запам'ятай образ: стрілка на папірці, і папірець живий, доки стоїть стіл. Ніхто не дивиться на те, чого вже нема.

> Папірець на столі — стрілка на папірці.
> Стіл пішов — стрілка щезає з ним.
> Нікому не потрібен погляд
> на порожнє місце.
> Усе живе свій строк і йде без шуму.

Спокійної ночі. До наступної зірки.
